Fifteen sensors,
and a mesh of one

Ragnar — the pentest and sensing box on a Raspberry Pi — already knows when someone is in the room, roughly how fast they're breathing, and when something on my network starts acting like an attacker. None of that could switch a light or buzz my phone, because it lived in Ragnar's own web page. This is how it became part of Home Assistant: fifteen native entities, four automations, and a mesh feature I switched on only to find I'd built a network with one member — until I found out why.

The shape of it

01Home Assistant never runs Ragnar code

The integration is a thin client. Every thirty seconds it asks the same web API the Ragnar dashboard already uses, and turns the answers into sensors.

That design is the reason I trust it. Nothing about the pentest tooling moves into the home-automation box; Home Assistant just logs in the way a browser would, keeps the session cookie, and makes read-only requests from then on. If the session expires it logs in again. If Ragnar is down, the sensors go unavailable and nothing else breaks.

I also chose not to install it through the community store, which would have pulled the newest version from GitHub. I copied the integration from the exact copy of Ragnar already running on the Pi, so the client and the API it talks to are guaranteed to be the same age.

Three small walls

02Things the docs didn't warn me about

None of these were dramatic. All three would have bitten later, quietly, if I hadn't checked.

I already owned the name. Months ago I built a small bridge that pushes Ragnar's scan counts into Home Assistant over MQTT, and one of its sensors was called ragnar_vulnerabilities. The new integration wanted the same name, so Home Assistant quietly gave it _2. An existing automation depends on the old one, so I renamed the new one instead of the other way round.

A settings screen that would have crashed. The integration's "Configure" dialog used a pattern Home Assistant removed late last year. It installs fine and runs fine; it only breaks the day you try to change the poll interval. I patched the two lines locally and wrote down that the patch has to be re-applied if I ever re-copy the integration.

The "event" that isn't an event. Security alerts arrive as an event entity — a sensor whose state is the time of the last alert, with the details attached. It does not fire anything on Home Assistant's event bus, so the obvious automation trigger would never fire. The working trigger watches the entity's state. It also needs a guard: when Home Assistant restarts, the entity restores its last alert, which looks exactly like a new one.

check what name you already own "installs fine" ≠ "every screen works" a restart can look like a new alert

The captive-portal rule triggers at medium on purpose: a portal that has only just been switched on scores "possible", not "confirmed", and I'd rather hear about it early. A keyword filter keeps routine medium alerts from setting it off.

The two I didn't build were the fun ones — hallway light on when someone's detected, and an LED strip that flashes red during an evil-twin attack. I don't own a light Home Assistant can turn red. Everything I have is on/off or brightness only, so the "flash red" became the voice pyramid's alert LED. Automations that point at lights that don't exist are worse than none.

The mesh of one

04I switched on a mesh with nobody in it

Ragnar can link several units over my private VPN so each one sees what its neighbours see. I turned it on. It reported one node reachable out of one.

Then I found a second Ragnar I'd half forgotten — a Pi Zero 2 W, online on the same private network, same software, same login. I switched the mesh on there too. It also reported a mesh of one. Two boxes that can reach each other perfectly well, each insisting it was alone.

The reason is deliberate. Ragnar doesn't treat "on my VPN" as "in my mesh". A unit only counts as a peer if it carries a specific tag in the VPN's access policy, because the tag is something only the account admin can grant. Neither of my boxes had it. Switching the feature on was necessary, not sufficient.

The built-in way to get the tag is to have Ragnar log the box back in to the VPN with a tagged key. I'm not doing that. Logging a node back in can hand it a new address, and the Pi 4's address is what Home Assistant and my message broker point at. Tagging the existing machines from the admin side keeps their addresses. There's a second trap in the same step: the Pi 4 uses the VPN's own SSH, and the default SSH rule doesn't cover tagged machines, so tagging it without adding a rule would lock me out of my own box.

Two days later I did it: declared the tag in the access policy, added the SSH rule for tagged machines, then tagged both boxes from the admin console. It took three saves. The first paste arrived scrambled — copying a long block out of a terminal had silently dropped chunks of lines. The second failed because I'd added the rule that uses the tag before the part that declares it. The third went through.

Found while checking

05Five hours of "unavailable" I didn't notice

Verifying the mesh in Home Assistant, every Ragnar sensor read unavailable — not just the mesh ones. Nothing to do with the tags: Home Assistant had restarted early that morning before the network was up, and the integration's first login timed out. Its client only treated network errors as "can't connect, try again later". A timeout isn't one of those, so Home Assistant saw a crash, gave up, and never retried. Fifteen sensors sat dead for about five and a half hours, and the only reason I noticed is that I happened to be looking.

The fix is two lines: treat a timeout as "can't connect" too, which tells Home Assistant to keep retrying on its own. After a restart everything came back — including someone in the room, and a mesh of two.

a timeout is a connection error "unavailable" is silent — nothing alerts on it

06Honesty notes

One key still expires. The Pi 4's VPN key never expires; the Pi Zero's still has an expiry date about five months out. Tagging an existing machine didn't clear it. That's one admin click, and it's on the list — a mesh node that quietly drops off the network in February is exactly the failure the tag was supposed to prevent.

The alert automations haven't fired for real. The entities are live and the rules are loaded, but no high-severity alert or captive portal has come through since. Until one does, the phone push and the pyramid voice are configured, not proven.

My phone push is still unreliable. The app I use only receives pushes while it's actively connected. Every alert also lands as a Home Assistant notification, so nothing is lost — but "it'll buzz my phone" is true only some of the time.

Turning a feature on is not the same as it working — look at what it reports back. The integration went in cleanly, and three quiet problems only showed up because I checked the entity names, the settings screen and the trigger type instead of trusting the install. The mesh was the same lesson in a louder form: "enabled" and "one node of one" were both true at once, until the boxes carried the tag. And a fourth problem — five hours of dead sensors — only surfaced because I looked. Nothing tells you a sensor has gone quiet; you have to go and see.
