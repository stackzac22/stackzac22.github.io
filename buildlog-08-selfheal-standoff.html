GhostGrid · Build Log 08 · 2026-07-29

Two self-healing systems fought —
and the reboot won

One node on the fleet kept rebooting itself. There was an obvious culprit sitting right there in the logs: a Wi-Fi crash on the hub upstream, timestamped minutes before every incident. That explanation was written down, believed for a day, and was wrong. The crash was the trigger. The cause was the node's own rescue mode — and underneath it, a recovery script whose every rung had never once worked, hidden because its last resort always did.

The trigger is not the cause

01A crash that only lasted a second

The upstream fault is real and it fired eight times in one day — eight crashes, eight malformed management frames, a perfect one-to-one match. It briefly drops the hub's access point. Yesterday's conclusion stopped there.

The problem with that story is arithmetic. A mitigation added the day before restarts the crashed service in about a second, so the access point was never gone for more than a moment. The node, meanwhile, was unreachable for 29 minutes before it rebooted itself. Something had to be holding that gap open, and it wasn't upstream.

The rescue ate the thing it was rescuing

02Rescue mode took the uplink radio

The node runs a monitoring loop that watches its own connectivity. Lose the network for long enough and it does the sensible field thing: raise its own access point so a human with a phone can still walk up and reach it. Sensible — on a box in a bag.

This box is not in a bag. It's a permanently-powered node whose whole job depends on staying joined to the fleet's private network, and it has exactly one radio doing that. When rescue mode fired, it took that radio, marked it unmanaged, and turned it into an access point. From that instant the node was no longer a client of anything. It could not rejoin the network it was trying to rejoin, because the hardware it would have used was busy being the rescue.

Thirty seconds later the other recovery system pulled the radio out from under it, and that restraint became irrelevant.

Masked by its own last resort

03The recovery ladder had never worked

The keepalive escalates in five rungs: unblock the radio, force the connection, restart the network manager, reload the driver, and finally reboot. Four of those five had never succeeded a single time in the entire life of the log file.

Once rescue mode marks the radio unmanaged, the network manager has no wireless device left to act on, so every "force the connection" rung fails on a device-not-found error. That error appears 48 times, going back to the log's very first lines. Nobody noticed, and the reason nobody noticed is the interesting part: the fifth rung works. The reboot genuinely does fix it, every time. A ladder where only the last rung functions looks, from the outside, exactly like a ladder that works — just one that always needs the big hammer.

The driver-reload rung had a second, self-inflicted bug worth naming. It stops the wireless supplicant to free the driver, reloads, then restarts only the network manager — never the supplicant. A network manager with no supplicant cannot bring up Wi-Fi at all, and the on-demand activation that should have covered for it failed too. So the rung meant to recover the radio was reliably leaving it in a state where nothing could recover it except a reboot. The escalation was manufacturing the condition that justified its own last resort.

a recovery step that can't verify it has a device to act on isn't a recovery step stopping a dependency without restarting it turns recovery into destruction a working last resort hides every broken rung above it
Ownership, not cleverness

04The fix was deciding who owns the radio

Nothing here was fixed by making either system smarter. Both were behaving exactly as designed. The bug was that two autonomous recovery systems had equal claim to one piece of hardware and no way to know the other existed.

Four changes, in order of leverage. Rescue mode is off on this node — it has three other ways home, so trading its uplink for an access point is a pure loss. Notably the software already had a flag for this; the flag was only honoured on a legacy code path and ignored by the loop that actually runs on a headless box, so it was unusable on precisely the machines that need it. That's now consistent, which makes it a fix for anyone running the same stack, not just us.

Then: the driver-reload rung restarts the supplicant it stopped. A new rung reclaims a hijacked radio — detects that something has turned the uplink into an access point, hands it back, and only then continues escalating. And it refuses to do that when a deliberate mode owns the radio on purpose, because wardriving and on-screen diagnostics both legitimately take it; a recovery system that fights intentional use is just a different bug. Finally the hub's access point moved off the channel the malformed frames arrive on — those announcements target a fixed default channel, and we were sitting on it.

05Honesty notes

Three, so this doesn't read as tidier than it is.

The reclaim rung is only partly proven. It was tested against a spare radio with a faked hijack, using an override added for exactly that purpose, with the destructive rungs gated off. Detection fired, the fake access point was torn down, the radio came back, and the live uplink never moved. What that does not prove is reclaiming the real uplink mid-hijack. That needs deliberate fault injection on a live node, and it hasn't been done yet.

The upstream crash is dodged, not fixed. The distribution ships only the affected version; the fix is in a newer upstream release that would have to be built by hand. Moving off the announcement channel means the frames don't reach the radio that was crashing — it does not mean the crash is gone. One of the hub's other radios still sits on a channel where the same class of frame is legal, and the source device hasn't been identified yet; its address is randomised. We're not publishing the frame or anything that would let someone reproduce the crash on other people's hardware.

The first explanation was ours, and it was wrong. "Upstream Wi-Fi crash took the node down" was written into the decision log a day earlier and believed. It survived because it was plausible, timestamped, and had a real defect behind it. What broke it was arithmetic — a one-second outage cannot produce a 29-minute gap — not new evidence. The correction is now recorded above the original entry rather than replacing it.

Two systems that each recover correctly can still take a node down, if nobody decided which one owns the hardware. Neither the rescue AP nor the keepalive was buggy in isolation — one raised an access point when the network vanished, the other escalated when it couldn't reach the gateway. Both correct. Put them on one radio with no shared notion of ownership and they produce a reboot loop that looks, in the logs, exactly like an upstream hardware fault. The lesson isn't about Wi-Fi. It's that autonomous recovery needs an owner and a way to check whether it still has the thing it's about to act on — and that a last resort which always works is very good at hiding the fact that nothing before it does.
