Real GPU acceleration in the browser,
finally — and it lost to the CPU

Build Log 04 hit a wall trying to GPU-accelerate a model natively on the phone: the Linux-side driver lied about supporting 16-bit float. This week Chrome's WebGPU finally started using real hardware on this laptop instead of falling back to software — including the exact fp16 feature that wall was built on. So I pointed it at the browser AI assistant already living in RaspyJack and measured it, live, against the CPU numbers from Build Log 05.

Confirmed, not assumed

01Is it actually hardware this time?

"WebGPU works" can quietly mean a software rasterizer (SwiftShader) pretending to be a GPU. Checked properly before trusting any numbers off it.

That last line is the whole story of Build Log 04 in reverse. The Adreno 630's Linux driver (Turnip) reported 16-bit storage as unsupported in the exact struct llama.cpp checks, and the model wouldn't even load. Here, on x1's decade-old Intel HD 520, Chrome's WebGPU backend reports shader-f16: true — for real, through the browser's own path (ANGLE → Mesa), not the native Vulkan path that hit the wall.

Decode speed held at ~3.5–3.7 tok/s across both runs — not a one-off shader-compile penalty on the first generation, but the browser path's actual steady state on this GPU. That's roughly a quarter of the CPU's throughput on the same laptop.

The anticlimax

03Real acceleration ≠ faster

It would be easy to call this a win because the harder problem — getting real fp16-capable GPU compute in a browser at all — is solved. But the honest read of the numbers is that the CPU is still faster on this hardware. Two likely reasons, not mutually exclusive:

HD 520 is a 2015 24-EU iGPU — weak even by integrated-graphics standards MLC's WebGPU compute kernels aren't as hand-tuned as llama.cpp's AVX2 CPU path browser sandboxing adds overhead native Vulkan wouldn't have

One caveat on the quality gap: the browser engine (MLC, q4f16_1) and the CPU engine (Ollama, Q4_K_M) are different quantizations of the same base model, not identical weights — so the nmap answer being right here and wrong on CPU isn't proof the GPU makes it smarter. Could easily be quant or sampling. The speed gap is the number to trust; the quality result is a data point, not a conclusion.

The actual next door

04Where this might still win

x1's Intel HD 520 was never going to be the interesting test case — it's the weakest GPU on the whole fleet. The genuinely open question is the one Build Log 04 already pointed at: the OnePlus 6T's Adreno 630, running Android's Chrome instead of Linux's Turnip driver. That's the side of the chip that exposes fp16 properly, per the driver-flag contradiction that build log dug up. Same browser assistant, same WebGPU path, a GPU that's actually modern instead of a decade-old laptop iGPU. That's the test that would actually tell you whether browser WebGPU is a real escape hatch from the native Vulkan wall — not just "does it run," but "does it run fast." Untested as of this log.

A capability existing and a capability paying off are two different claims. WebGPU going from fake to real on this laptop is a genuine unlock — it's the same fp16 gate that blocked native inference entirely on the phone. But "it runs" isn't "it's fast," and on this particular iGPU the CPU still wins. The next real test isn't this laptop — it's the phone, on the driver that was never the problem in the first place.
