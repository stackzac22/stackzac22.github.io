The screen wasn't broken —
the build was

A mesh radio came up with a dark screen and never showed the pairing number the phone app was waiting for. Every symptom pointed at a dead display: right board, right cable, right port, nothing on the panel. The display was fine. I had flashed it as a different product — one whose defining feature is not having a screen. Fixing that unlocked the rest of the night: a private channel to a friend's node, an internet bridge, and a clear lesson about what a bridge is not.

The symptom pointed at hardware

01A radio that wouldn't say its number

Pairing a mesh node to the phone app is a two-way handshake: the app asks to connect, the node prints a six-digit number on its own screen, you type it in. No screen, no number. No number, no pairing.

The board enumerated cleanly over USB, took a flash without complaint, and answered on the serial console. So it wasn't dead, wasn't a cable, wasn't a port. It just never lit the panel — and because the panel is the only place the pairing number can appear, a working radio was completely unreachable from the app. The obvious read was a failed display or a bad solder joint on a cheap board, and I nearly went looking for one.

Two products, one build target

02I flashed the version without a screen

The firmware project no longer ships a standalone build for this exact board. What it ships is two builds for the same chip family — and one of them is for the variant that has no display at all.

The sibling product is the Lite: same processor, same radio, same footprint, no OLED. Its build therefore contains no display driver, because on the hardware it targets there is nothing to drive. Flash it onto a board that does have a panel and you get precisely what I got — a fully functional radio, correctly running, that never initialises the screen. The board was reporting itself as the Lite because I had, in every sense that matters, told it that it was one.

This is the part I want to keep. Nothing in the failure looked like a software choice. A dark panel reads as electrical, and I had already started reasoning about hardware faults before I thought to ask what the running firmware believed it was. The board answered that question the moment I asked it directly — the device identity was right there in the boot banner, and it was the wrong product name.

The fix is an erase and a clean write of the factory image for the screened target. Worth knowing before you do it: a full erase takes the configuration with it. Channels, region, module settings — all of it. I had that scripted, so it cost a minute; unscripted it would have cost the evening, and I would have been re-entering settings I only half remembered.

# erase first — a plain overwrite can leave stale config behind
esptool --chip esp32s3 --port /dev/ttyUSB0 --baud 460800 erase-flash
esptool --chip esp32s3 --port /dev/ttyUSB0 --baud 460800 \
        write-flash -z 0x0 firmware-<screened-target>-<version>.factory.bin

# then re-apply config — the erase wiped it
./configure-node.sh /dev/ttyUSB0

It booted as the right product, the panel came up, and the pairing number appeared the instant the app asked for it. One note for anyone matching symptoms: the physical panel on this board is a small one, so the interface renders into the top region rather than filling the glass. That's correct behaviour, not a second bug — I checked, because by then I didn't trust anything.

"right board" is not the same as "right build" ask the firmware what it thinks it is before suspecting the solder a missing driver looks exactly like dead hardware
The thing I'd been burned by before

03A private channel, written down first

With the node pairing again I set up what it was bought for: a private encrypted channel shared with a friend's node, so the two of us have a link that doesn't depend on anyone's cell network.

The channel is a name plus a key. Anyone holding the key can read the traffic, which makes it exactly as private as your handling of it — so it lives in a local-only repository that has no remote and is never pushed anywhere, and it reaches my friend as a QR code they scan once. It is not in this post, and it will not be in any post.

The reason I was careful is that I'd already made the opposite mistake. I handed a node to a friend once without recording its channel anywhere, and when I went looking months later there was nothing to find — I searched every log I keep and turned up a single commented-out example line. That node and I had no shared channel at all, and no way to make one remotely. Setup you don't write down isn't setup; it's a thing you'll do again from scratch, later, without the device in your hand.

So this one got the full treatment: key recorded locally, QR generated, and a one-page joining sheet written for a person who does not run Linux and should not have to. The sheet uses the "add" path rather than "replace" deliberately, so joining my channel doesn't wipe the default one their node already talks on.

A bridge is not an antenna

04What the internet bridge actually bought

The node can also relay its mesh traffic to an internet broker, in both directions. I turned that on for the private channel. It is genuinely useful and it does not do the thing I initially assumed it did.

What it buys: anything the node hears on the mesh can leave the mesh, and anything sent to the broker can come back down onto it. That's remote monitoring, and it's the path for alerts and telemetry from the rest of the grid — a motion trip, a battery level, a status ping. What it does not buy is range. Two radios still have to be in radio reach of each other to talk directly. The bridge extends where the data can go, not where the radio can reach, and I spent a few minutes genuinely confused about why a friend's node still wasn't appearing before that distinction landed.

It also cost something I didn't expect. This chip has one radio for both Wi-Fi and Bluetooth, and turning Wi-Fi on to reach the broker turned Bluetooth off. The pairing number I had just spent the evening recovering became irrelevant, because the node no longer speaks Bluetooth at all. It's now managed over USB or over the network instead. That's a fine trade for a node that sits on a shelf — but if this were a device I carried and configured from my phone, enabling the bridge would have quietly taken away the only way I manage it.

05Honesty notes

Three, because this one ends less finished than it sounds.

The link is built but unproven. My side is configured, keyed, and bridged. The friend's node is out of radio range and they can't easily do their half of the setup, so not one message has crossed this channel yet. What I've actually verified is that my end is correct and reproducible — not that the two nodes can talk.

The node can't join my private network. It's a microcontroller; the mesh VPN the rest of the fleet lives on has no client for it. Reaching it from outside the house means routing to it through something that can run one, or a jump host. That's not a problem for the mesh itself — the broker is on the public internet — but it does mean this node sits outside the tidy story the rest of the fleet tells.

I flashed the wrong build in the first place because I trusted a name. The two targets differ by a few characters and both look plausible for the board in your hand. I didn't check what the second one meant. Nothing about the failure that followed would have led me back to that choice on its own, which is the whole reason it's worth writing down.

A missing driver and dead hardware produce identical symptoms — and only one of them is visible from the boot banner. The screen was never broken. I had flashed the board as its screenless sibling, so the firmware simply had no display code in it, and every downstream symptom — dark panel, no pairing number, unreachable from the app — followed from that one wrong choice made in a menu, minutes earlier. Ten seconds reading what the device said it was would have skipped the entire hardware theory. The same evening's other lesson rhymes with it: a bridge moves your data somewhere new, it does not move your radio, and the difference only becomes obvious when you're staring at a node that still isn't there.
