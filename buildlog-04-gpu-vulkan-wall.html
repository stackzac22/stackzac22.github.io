Trying to GPU-accelerate Ragnar,
and the wall I hit

Ragnar's 7B model runs CPU-only on a rooted phone — it works, but it pegs all eight cores and takes the better part of half a minute to warm up. The phone has a GPU sitting right there, doing nothing. So: offload it to the GPU with Vulkan and get a free speed-up. Here's the wall I hit, and the twist that moved it.

A good clue

01The GPU was already lying to me

Before touching anything, I checked what the phone's existing LLM runtime thought about the GPU.

Vulkan support was already switched on in the runtime — but it was silently falling back to CPU. Its GPU detection only ever looked for an NVIDIA card, which a phone obviously doesn't have, failed, and quietly gave up. The actual Vulkan backend library was never even installed. So step one wasn't "enable the GPU," it was "find out why it pretended the GPU didn't exist."

Good news underneath that: the phone runs full Linux (Kali/NetHunter), and the open-source GPU driver stack — Mesa's "Turnip" Vulkan driver — was present and healthy. The GPU enumerated cleanly as Turnip Adreno (TM) 630.

02Building the real thing

Rather than fight the existing runtime's missing pieces, I built the reference engine from source, on the phone itself, with the Vulkan backend turned on.

That meant installing a compiler toolchain, the Vulkan dev headers, a shader compiler, and the SPIR-V headers — then a long compile on an 8-core phone. It built clean.

llama.cpp · from source Vulkan dev headers glslc SPIR-V 8-core compile
The wall

03It refused to even load

Asked it to load the 7B model onto the GPU. It refused — the model wouldn't load, let alone run faster.

ggml_vulkan: device Vulkan0 does not support 16-bit storage. error: failed to load model

It was so insistent that just having the Vulkan backend loaded broke the CPU path too, until I explicitly hid the GPU from it.

The twist

04It's the driver, not the GPU

Almost wrote this off as "old GPU can't do it." Then I actually read the driver's own feature flags — and they contradicted themselves.

Extension check VK_KHR_16bit_storage → true

The Turnip driver advertises 16-bit storage support through the Vulkan extension query.

Core feature struct storageBuffer16BitAccess → false

But reports false in the core feature struct that llama.cpp actually checks — so it sees "false" and bails.

That reframed the whole thing. The Adreno 630 isn't the wall. The wall is which driver you're running — the same chip tells two different stories depending which side of the phone's OS split you ask from:

Linux · NetHunter/Kali

Where Ragnar lives. The GPU uses the open-source Mesa Turnip driver — and on this chip, Turnip doesn't cleanly expose fp16 to apps.

Android · same silicon

The exact same GPU, Qualcomm's proprietary driver — which exposes fp16 properly. That's how phone-LLM apps that do use the GPU pull it off: they run on Android, not the Linux side.

05Where it stands

Ragnar stays on CPU for now — it was already working. But "GPU is impossible on this phone" turned out to be wrong: it's "GPU is impossible on the driver my Linux slot uses." The same phone has an Android slot with the proprietary driver, worth testing as the place the GPU actually earns its keep. The catch: the two slots don't run at once, so it's a real architecture question, not a flick of a switch.
